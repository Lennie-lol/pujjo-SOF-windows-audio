## ADL-N IPC4 and routing evidence

The boot candidate is Intel-signed SOF IPC4 2.12, `adl-n/intel-signed/sof-adl-n.ri` from `sof-bin`. Its Git blob is `47bb69dd2e22435e6da37ccee17103e0f6452638`, size 707036 bytes and SHA-256 `bc83cffa1bb5a4a8da24bbc7bb7040bd744f1e0c63e3d16151d1769ac8ae8214`. The manifest reports ADSPFW 2.12.0.1 and 25 modules. The UUIDs resolve to copier ID 4 and gain ID 6. The reviewed boot build checks the digest before staging DMA. ROM authentication, FW_READY and a successful version query still require target hardware evidence. [Firmware artifact](https://github.com/thesofproject/sof-bin/blob/fcd5ae85ead7ecd67ff199335b61fac825843ca0/v2.12.x/sof-ipc4-v2.12/adl-n/intel-signed/sof-adl-n.ri)

Linux identifies the same controller as ADL-N, supports IPC3 and IPC4, and defaults to IPC3. The Chromebook audio project installs its downstream board topology into the IPC3 topology directory. That topology contains the SSP1 speaker, SSP0 headset and SSP2 Bluetooth routes, and a DMIC route. The SOF IPC4 v2.12 distribution has no corresponding ADL-N RT1019P/RT5682S topology. Linux can read NHLT capability records embedded in an IPC4 topology manifest. This driver uses exact PCM matches from a validated ACPI NHLT table and has no approved board-specific IPC4 topology fallback. ## First native validation stage

Keep installation deferred until an authorized diagnostic package has passed WDK builds, INF and catalog verification, and signature validation. Retain recovery access and confirm that Windows can remove the exact package before an experimental device is bound.

1. Capture SMBIOS and PCI identity, translated BAR and IRQ resources, NHLT bytes if present, and the codec and amplifier Resource Hub assignments. Record whether DMIC or SSP entries contain exact PCM configuration blobs.
2. With an authorized read-only peripheral probe, read the RT5682S identity registers and record transfer status and byte counts. Record the amplifier GPIO connection without driving it.
3. In a separate guarded session, keep audio endpoints disabled. Record the ROM acknowledgement, code-loader and ICCMAX DMA stop confirmations, FW_READY and the returned firmware version. Treat a missing acknowledgement or configuration response as a failed boot.
4. Qualify the supported PortCls device lifetime and DMA ownership before exposing an endpoint. Validate real DMIC DMA progress and input first if its format and configuration are available. Qualify RT5682S clocks, DAC/ADC paths and jack transitions before headset testing. The speaker requires verified SDB polarity and timing, calibration and an independently established safe gain limit before any audible run.

The ordinary build keeps DSP activation locked. The inherited PortCls registration and WaveRT activation gates remain locked pending framework and device-lifetime qualification. No distribution package is generated by the compile-only workflow.

## Boot and stream validation boundaries

The code loader polls its playback descriptor with the stream IRQ masked. It checks the programmed routing, tag, buffer size, format, descriptor list and SPIB credit before RUN. FIFO and descriptor faults abort boot. The IPC interrupt handler acknowledges FW_READY, then the loader queries BaseFW configuration and compares the running version with the manifest before opening IPC to normal callers.

The guarded DMIC stream reads the Intel decoupled host DMA position register and polls hardware completion status. The NHLT lookup requires matching container and valid-bit depths as well as consistent block alignment and byte rate. A single-pipeline graph uses firmware pipeline deletion to remove its internal routes. These changes have host coverage for configuration and failure paths. The kernel gates still require a supported PortCls device and DMA lifetime integration before WaveRT can be used on hardware. [Intel HDA position selection](https://github.com/torvalds/linux/blob/v6.13/sound/soc/sof/intel/hda-stream.c) · [IPC4 route teardown](https://github.com/torvalds/linux/blob/v6.13/sound/soc/sof/ipc4-topology.c)

## Windows inventory without NHLT

On Pujjo rev3 the firmware-table export returned Win32 error 1168. Windows enumerated MCFG, FACP, APIC, DMAR, HPET, SSDT, TPM2, LPIT, DBG2 and BGRT. The PCI driver now tries a build-time topology configuration on a missing-table result. Malformed ACPI and unrelated errors bypass the fallback. A successful fallback owns its own allocation and uses the same parser, exact endpoint matching and release path as ACPI.

The Chromebook Linux topology (SHA-256 `cdaf9b8274aa0be0f6406db1cf9ad405e0bde2626c8e106793d3238db27db1e5`) contains a three-byte IPC3 manifest. Its SSP hardware records specify the following values.

| Link | MCLK | BCLK | Frame clock | Slots | Valid sample bits |
|---|---:|---:|---:|---:|---:|
| SSP0 headset | 19.2 MHz | 2.4 MHz | 48 kHz | 2 × 25 | 24 |
| SSP1 speaker | 19.2 MHz | 3.072 MHz | 48 kHz | 2 × 32 | 32 |

Its 48 kHz DMIC record enables both microphones on PDM controllers 0 and 1. The Pujjo firmware source selects the `_2ch_pdm0` microphone topology for the RT1019/RT5682 variant. The current Windows headset implementation qualifies direct 24.576 MHz MCLK. Applying the Linux archive unchanged would conflate these configurations. The exact topology selected in the original Pujjo ChromeOS image remains to be established. [Pujjo board selection](https://github.com/coreboot/coreboot/blob/main/src/mainboard/google/brya/variants/pujjo/overridetree.cb) · [Chromebook Linux topology](https://github.com/WeirdTreeThing/chromebook-linux-audio/blob/84b700e271145df82ae71d0497af11705a2bb166/blobs/adl/sof-adl-rt1019-rt5682.tplg)

An IPC4 topology can carry a type-1 NHLT manifest item. To import a reviewed artifact, run `python scripts/build_pujjo_topology_config.py SOURCE.tplg REVIEWED_SHA256 src/driver/PujjoReviewedTopologyNhlt.h`, review the generated endpoints and firmware compatibility, then compile with `PUJJO_REVIEWED_TOPOLOGY_NHLT`. The digest identifies the input. Board compatibility requires separate evidence. No topology table is approved in this revision. The importer accepts bounded ALSA v5 manifests and preserves endpoint bytes, including format-specific gateway configurations. Upstream ALSA emits an unassigned ACPI header in topology output. The importer finalizes its checksum, and the driver validates the resulting table before use. [Linux IPC4 manifest handling](https://github.com/torvalds/linux/blob/v6.13/sound/soc/sof/ipc4-topology.c) · [Intel NHLT encoder](https://github.com/alsa-project/alsa-utils/tree/master/topology/nhlt/intel)

A translation from IPC3 requires reconstructing the SSP register/divider program and DMIC controller/filter coefficients for the selected ADL-N clock source. The IPC3 link descriptors supply framing and desired frequencies. They do not specify the complete IPC4 register blobs. The Intel encoder's padding and divider selection must reproduce the requested bit clock, including the unusual 25-bit headset slots. The v2.12 IPC4 package has other ADL profiles and an MTL RT1019 profile. None identifies this ADL-N Pujjo variant. IPC3 is a separate backend option on ADL-N. It would need a reviewed signed IPC3 image, IPC3 ready/ABI handling, DAI configuration, component and PCM messaging, stream triggers and teardown. The existing Windows PortCls and DMA ownership can be reused. Changing only the firmware filename or topology parser cannot switch the IPC protocol.
