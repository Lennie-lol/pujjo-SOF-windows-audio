# Remaining blockers — v0.0.16

Not ready to install or conduct audible hardware validation. Ready for offline review and a compile-only Windows CI attempt. The following work is required before controlled Chromebook testing; further issues may emerge during WDK compilation or measurements.

1. Obtain successful VS2022/MSVC Debug and Release x64 builds with SDK/WDK 10.0.26100. Resolve real WDK ABI, SAL, warning and PortCls/KMDF lifecycle issues. Run Microsoft driver analysis and review the resulting imports/entry point. The host WDF doubles cannot establish any of these.
2. Establish board-specific Windows PnP resources, MCLK/BCLK/FSYNC measurements, SSP0/SSP1 pinmux, polarity, amplifier rails and reset behavior. Linux SSP routes are candidates only. No hard-coded GPIO or bus addresses may substitute for assigned resources.
3. Complete the ADL-N signed firmware trust/compatibility policy, manifest extensions and segment validation, ROM authentication/error handling, DSP power/reset sequencing, code-loader DMA descriptor/stream programming, interrupts and bounded boot recovery. The metadata parser does not authenticate firmware or authorize boot. A valid filename/hash alone is insufficient.
4. Implement and verify the firmware's IPC4 mailbox/notification protocol, READY capabilities, module UUID discovery, pipeline creation, payload layouts and shutdown/recovery. Existing IPC/topology prototypes are not demonstrated compatible with this firmware. Linux topology blobs cannot be loaded as Windows endpoints without an explicit translation/design.
5. Finish RT5682S reset, rail/bias timing, identification, masked initialization, PLL power/lock, sysclk selection, serial format, routing, headphone output, capture path, calibration, jack detection and power restore. The new coefficient planner does not implement these stages or select a board clock automatically.
6. Validate RTL1019's rt1015p-family enable/shutdown GPIO polarity and calibration timing against the actual circuit. Implement measured safe startup, conservative gain, mute-before-enable, fault-off recovery and sleep/wake in the real driver. Mock successful disable cannot prove that a speaker is electrically off. Do not use the unrelated rt1019.c register driver as the RTL1019P path.
7. Replace mock coordinator callbacks with a reviewed cross-device Windows architecture that owns references and serializes PnP, D0/D3, cancellation, removal, firmware and codec/amp state. The coordinator is not linked into the kernel; do not simply remove its host-only guard.
8. Complete PortCls/WaveRT endpoints, formats, render/capture DMA, position/timestamps, buffer ownership, notifications, hardware-backed mute/volume, conservative gain and stream teardown. No end-to-end render or microphone capture has been established.
9. Prove DMA/ISR/DPC quiescence before releasing resources on every timeout, stop, surprise removal and power failure. Allocation improvements do not prove the surrounding engine lifecycle safe. Review lock ordering under Driver Verifier and real WDF, not only pthread doubles.
10. After compilation/design review, prepare a separate controlled, initially muted validation plan with recovery access, measured clocks/power, debugger and Driver Verifier. Then test suspend/resume, unplug/removal, failures and HLK/audio certification as applicable. Never infer hardware readiness from the host test counts.
